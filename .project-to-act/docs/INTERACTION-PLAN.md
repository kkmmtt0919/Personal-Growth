# 本地任务交互实施与验收

2026-10-06。用户选择“任务操作与提交闭环”，I1–I5在独立受控本地范围完成实现与质量门复核。阶段证据见 `artifacts/interaction/i5/README.md`（EV-087）；真实模型交互效果、完整MVP与发布尚未验收。只读Demo原契约继续保留。

## 建议先做任务操作与提交闭环

用户从现有 Growth Loop 开始一个 proposed 任务，提交验收产物，页面展示闭环结果及其证据来源。已有任务状态机与 TaskLoop 可复用，避免同时引入目标澄清、独立材料上传与 Mentor Chat。

原只读 `api/app.py` 和 `api/local.py` 契约保持不变。交互入口为 `api/interactive.py`，任务页按服务配置展示操作与提交，使用独立实验库。

实施更新：任务页已按交互服务配置显示状态操作、理解表单和文件选择器。`POST /api/tasks/{task_id}/files` 接收严格JSON文件内容（base64），流式限制请求体3 MB，解码后限制2 MB；格式匹配、UTF-8与路径检查先于入库。文件只落在独立实验目录的服务器生成路径，随后调用既有TaskLoop。`--with-practice` 创建尚未提交的实践场景，默认老场景与只读Demo种子保持兼容。验证见 `artifacts/interaction/README.md`。

## 分步交付

| 小步 | 交付 | 验证 |
|---|---|---|
| I1 | 独立实验库与交互服务，复用 GrowthStore 的任务状态迁移；提供激活、阻塞、恢复、放弃操作 | 非法迁移拒绝，未知任务拒绝；原只读服务仍无写路由；历史 Demo 内容不变 |
| I2 | 首先支持文本理解回答提交，调用 TaskLoop.complete_task；明确处理中、成功、失败三种结果 | 状态非 active 拒绝；失败不伪报 done；重复/并发请求不重复执行模型或形成两份提交 |
| I3 | Growth Loop 接入操作与提交表单，读取实际结果，刷新任务、证据与两维度等级 | 完成但未升星仍正确展示；错误可理解；刷新后可读取归因；390px和桌面操作可用 |
| I4 | 接入实践产物文件提交并保存可追溯结果 | 服务器接收文件后生成内部路径；客户端不得指定服务器文件路径或 source_id；证据来源可反查 |
| I5 | 独立库端到端演示与质量门复核 | 提交→source→claim→binding→assessment 全链；失败/重跑；audit pass；原库逐表内容不变 |

I1 可在零模型请求下实现。I2 起绑定继续使用既有网关，每次提交最多一次 HTTP，失败停止，不自动重试。真实模型验收需沿用已确认的预算并独立记录，不以离线夹具结果冒充模型验收。

## 既有契约继续生效

- 任务状态按既有状态机处理；done 只能由完整 TaskLoop 链尾落定。
- 任务完成不直接修改等级。变化展示同时需要前评定、新证据 provenance、后评定。
- 绑定继续走 ClaimBinder 闸门，评级继续走 AssessmentPipeline，不增加 API 直接写 assessment 的路径。
- 提交与归因应从持久化链派生。现有只读 Demo 的 manifest 报告不能充当新提交结果。
- 请求串行化范围、模型运行中的重复请求处理、重启后失败恢复须在 I2 实现前明确；不能用仅隐藏按钮来保证幂等。

## 尚需确定的优先级

若优先选择材料上传，则先设计材料归属、输入格式和证据接入结果，再接独立上传页面。若优先选择目标澄清，则先接 Goal Agent 的轮次与显式确认状态机，再展示能力树。两者不与任务交互同时开工。

Mentor Chat、Memory 演化、目标自动重建、OAuth、外部通知与云端发布继续留在各自后续阶段。
