## 0. 先回答核心问题：M3 在回答什么？

> **M3 到底是在回答"用户有什么能力"，还是回答"这些能力有什么证据可以证明"？**

### 建议判定：**M3 回答后者 —— 证据准入与断言绑定；"用户有什么能力"（星级）留给 M4。**

| 读法 | 内容 | 与既有设计的关系 |
|---|---|---|
| **A（推荐）：证据准入** | 把 Chat/Upload/GitHub 三条通道的原始材料变成**可追溯的证据链**，并绑定到它能支持的 claim（断言）。输出：`source → passage → evidence → claim` 完整且 audit pass。**不产出任何星级** | 与验收门一致：G2（可追溯）与 G3（识别"自称会但证据不足"）的负责里程碑都是 **M4**；M3 的 ROADMAP 完成条件也只要求"产出 passages / 技术栈清单 / ≥3 条 capability claim" |
| B：能力评估 | M3 直接回答"用户具备几星" | 把"证据存在"与"能力等级"混为一谈 —— 这正是 PRD §10 与 §33 警告的失败模式；且会与 M4 的 G3 对照实验重复，M3/M4 边界消失 |

**为什么推荐 A（三条理由）**：
1. **产品语义正确**：证据只能回答"有没有依据、依据多强"，星级还要经过"证据类型分层 + 反向证据 + 攻击裁决"（PRD §10），那是 M4 的内核。
2. **M2 已经铺好了 M4 的输入**：`g_capabilities`（目标能力树）已在库中；M3 把证据与 claim 挂上去，M4 才能做 `g_capability_claims` 桥接与 `g_assessments` 评级。
3. **归属层是数据问题，不是推断问题**：M3 有资格定"这份产物算不算用户证据"（由用户动作显式声明），但没资格定"用户多强"。

**若你选 B**，需要接受：M3/M4 合并（或 M3 变成 M4 的第一半）、G3 对照实验前移、范围显著变大 —— 建议在确认时明确。

## 1. 目标（按读法 A）

**三条输入通道可用，且进来的一切都能追溯到原始材料、并清楚标注"它是不是关于用户本人的证据"。**

一句话：**M3 回答"这些能力有什么证据可以证明"——把证据接进来、把断言绑上去、把归属说清楚；不回答"用户几星"。**

## 2. 范围

### 2.1 做

| 项 | 内容 |
|---|---|
| 通道一：Upload | PDF / Markdown / TXT / 代码 / ZIP 走 `adapter` 单入口入库；富格式经 evkg V1 状态机；代码走 `SourceKind.CODE` 快路径（M1-b.5a 已建） |
| 通道二：GitHub | OAuth（最小权限）+ 选仓库 + 拉取 README/源码/提交 → 入库；token **只存引用**（`g_integrations.secret_ref`） |
| 通道三：Chat（材料化） | 对话中的自述/资料入库为 `chat_assertion`（弱证据，独立通道，不得单独支撑结论） |
| 领域资料（JD） | 入库标 `domain_reference`，**不产生用户能力断言**（R5 决策的 M3 落地） |
| **归属层** | 新增显式归属字段与规则（见 §3）：`user_declared` / `user_asserted` / `unknown` |
| 断言绑定 | 由证据生成 claim 并使 `claim → evidence → passage → source` 可逐跳追溯（审计 pass） |
| 检索 | 入库后可检索（`find_sources` metadata + FTS 索引，M1-g 已验证索引可用） |
| 证据记录 | 每次入库写 `g_agent_runs`（若经 Agent）与 metadata 标签；技术栈清单落库 |

### 2.2 不做（明确）

- **不产出任何星级、不做 assessment**（M4；G2/G3 的门也不在 M3 判定）。
- 不生成任务（M5）、不做 UI 页面（M8；M3 的 UI 仅"仓库选择"所需最小交互，见 §5 决策 3）。
- 不做向量检索 / RAG 问答 / 知识库问答（架构非目标：先用 FTS5 + 结构化查询）。
- 不把 JD/岗位资料转成用户能力断言；不由"项目存在"推断"用户实现"（归属层只记录声明，不推断）。
- 不处理 M2 遗留的"再生成并集语义"（用户 2026-10-02 明确：留到能力审计/演化模型统一决策）。
- 不引入多用户/权限体系（Q4）。
- 不修改 evkg 上游逻辑（保持 M1 的有条件依赖 C1–C5；如需改动走上游提案）。

## 3. 归属层（M3 必须定的数据决策）

问题：`repo_artifact` 只能证明"这份产物存在"，不能证明"用户本人实现"。M1-d 已实测：抽取器会（正确地）
拒绝把项目成果归因为个人能力，且攻击环节会推翻越权主张。M3 起用户证据开始真实流入，必须先有**显式的归属记录**。

建议（需确认）：

| 归属取值 | 产生方式 | 消费规则 |
|---|---|---|
| `user_declared` | **用户动作**：亲自上传某文件 / 授权并选择某仓库 | 可作为实践/任务证据支撑 claim |
| `user_asserted` | 用户口头声称（聊天）但无产物 | 只能作为 `chat_assertion` 弱证据，不得单独支撑结论 |
| `unknown` | 第三方资料、领域参考（JD/论文/官方文档） | 仅作 `domain_reference`，**不参与**用户能力断言 |

- 存储：`Source.metadata` 上加 `growth_attribution`（与既有 `growth_evidence_type` / `growth_channel` 并列），
  必要时在 `g_` 表族建一张归属记录表（含 `declared_at` / `declared_by` / `declaration_kind`）。
- **纪律**：归属是"用户声明的记录"，不是"系统推断的结论"；系统不得据其他线索自动升级归属。

## 4. B-g2（PDF spike）的位置

M1-g 把"富格式路径 0 端到端验证"列为**阻塞 M3 的前置项**（B-g2）。建议：

- 作为 **M3-a（前置 spike）**，通过标准三条：
  1. 真实 PDF（含中文）经 evkg V1 状态机入库，产出 passages；
  2. `audit_store` = pass（引文/引用/结构不变量 0 violation）；
  3. 能说明该路径下 locator 的可核对性结论（V1 归一化会重排文本 → 需明确"PDF 的 locator 是否可回原文核对"，不能含糊）。
- 若 spike 不通过：M3 的 PDF 部分**降级**为"仅 Markdown/TXT/代码/ZIP"，并如实报告缺口（不硬撑、不降低 locator 标准）。
- 依赖：需要新增 `evkg[office]`（pypdf/python-docx/openpyxl）→ 会改 `uv.lock`（需你确认，见 §5 决策 2）。

## 6. 验收标准（草案）

### 6.1 ROADMAP M3 完成条件（硬性）

1. 上传一份 PDF 与一份 Markdown，均产出 passages **且可检索**；
2. 上传一个代码 ZIP，能抽出技术栈证据；
3. GitHub 授权并选择仓库后，自动产出技术栈清单与 **≥3 条 capability claim**；
4. 未授权仓库的数据不被读取；token 不以明文出现在账本/日志；
5. 上传的领域资料（如 JD）标为 `domain_reference`，**不产生**用户能力断言。

### 6.2 本步质量门（沿用 M1/M2 纪律）

6. 归属层：三条归属取值的消费规则各有测试（`unknown` 不得支撑用户断言；`user_asserted` 不得单独支撑结论）；
7. `claim → evidence → passage → source` 逐跳可追溯（自动化测试）+ `audit_store` = pass/0；
8. LLM 路径离线回归（fake gateway）+ 真实运行单独留档（沿用 M2 的两层预算与"失败即停"规则）；
9. 依赖与数据边界：真实用户库不被测试污染（沿用 M2-a 的零写入断言）；`audit` 前后证据表逐表哈希一致；
10. 复用 M2 的运行记录纪律：`g_agent_runs` 记录实际 provider/model，失败也留档。

### 6.3 明确不在 M3 判定的

- G2（可追溯性）与 G3（A/B 对照实验）的**门判定**仍属 M4；M3 只产出它们所需的证据。
- 星级、缺口、任务：M4/M5。

## 8. 风险与前置

- **前置（阻塞）**：B-g2（M3-a）；GitHub 凭据（M3-d 起）；`evkg[office]` 依赖确认。
- 富格式 locator 的诚实性：V1 归一化会重排文本 —— 若无法保证 locator 可回原文核对，必须如实标注该路径的局限（M1-b.5a 的纪律：一个说谎的 locator 比没有更糟）。
- ZIP 代码：需要遍历 + 逐个走 `ingest_path`（已是现成能力）；注意大仓库的调用量控制。
- GitHub API 速率限制：需退避与增量策略（MVP 只取默认分支的 README/源码/近期提交）。
- 不把 M2 的"并集语义"带进 M3：M3 不解决它，但要在 `g_capabilities` 与新证据的关联上避免做出与未来决策冲突的假设。
