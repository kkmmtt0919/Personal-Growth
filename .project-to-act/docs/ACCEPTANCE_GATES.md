# Growth OS 验收标准与证据链

> 把 PRD §33 的 6 条"核心成功标准"翻译成**可执行、可证伪、带证据**的验收门。
>
> 状态：**待用户确认**
> 关联：`ROADMAP.md`（哪个里程碑负责哪道门）· `ARCHITECTURE.md`（系统结构）

---

## 1. 验收原则

对齐 project-to-act 的完成门契约：

> **没有新鲜证据就不算完成。** 失败、跳过、过期、未知、未记录的证据都不构成完成。

具体到本项目，一条验收记录必须包含：

| 要素 | 要求 |
|---|---|
| 证据 ID | 唯一标识，落 `PROJECT_ACCEPTANCE.md` 的证据索引 |
| 时间 | 新鲜度（过期证据需重跑） |
| 方法 | 可复现的命令或操作步骤，不是叙述 |
| 退出状态 | 实际输出，不是"我确认通过" |
| 版本/哈希 | 代码 commit 或产物哈希，保证可定位 |
| 位置 | 产物路径（日志、截图、dossier） |

**反模式（明确禁止）**：

- ❌ "已实现 X 功能" —— 无证据
- ❌ "测试通过" —— 无输出
- ❌ 用一次成功的截图代表一个能力门 —— 单点不构成覆盖

## 2. 用 evkg 自身承载验收证据（产品自举）

这是本项目的特色：**验收过程本身走一遍证据链**。

```
验收动作（跑测试 / 演示 / 截图）
        ↓ 作为 source 入库
   data/acceptance.db      （独立于用户证据库，避免污染）
   profile: growth_acceptance.yaml
        ↓
   Claim: "Growth OS 通过 G3 能力审计门（版本 v0.x, commit abc123）"
        ↓
   Evidence: 测试输出 / 运行日志 / 截图 / 前后 assessment 对比
        ↓
   Attack:  "这条结论有什么证据？证据是否只是自述？样本量够吗？
            有没有反例没被覆盖？是不是只跑了 happy path？"
        ↓
   Dossier: 验收档案（Markdown）
        ↓
   作为 PROJECT_ACCEPTANCE.md 的证据索引条目
```

**为什么值得这么做**：

1. 验收结论自己也是"带攻击的可审计断言"，而不是一句自我声明；
2. 在 M1 就顺带验证了 evkg 的完整能力（等于给 M1 加压测试）；
3. 是 PRD §33 第 2 条（证据可追溯）的自我兑现 —— 连"我们做完了"这件事都可追溯。

**注意**：`acceptance.db` 与用户证据库物理隔离。项目验收证据**绝不能**进入用户的能力断言通道，否则会污染 G3 的判定。

## 3. 产品验收门（对应 PRD §33）

### G1 · Goal Clarification

> 用户能否从一句模糊目标，得到一个明确目标？

| 项 | 内容 |
|---|---|
| 场景 | 冷启动用户，只说一句"我想成为 AI Agent Engineer" |
| 判定 | 系统在 **≤6 轮**内产出 confirmed goal，且目标包含 {方向, 目的, 时间周期, 可衡量结果} |
| 证据 | `g_goal_clarifications` 完整往返轨迹 + `g_goals` 记录 + 会话截图 |
| **反例（必须不通过）** | 系统直接落库一个模糊目标，或未经用户确认就进入能力分析 |
| 负责里程碑 | M2 |
| 证据存放 | `artifacts/gates/G1/` |

### G2 · Evidence Traceability

> 每个重要能力判断是否都能追溯到真实证据？

| 项 | 内容 |
|---|---|
| 判定 | 随机抽 **5 条** assessment，每条都能沿 `assessment → claim → evidence → passage → source` 追溯到原文 |
| 自动化 | 写成测试：`tests/test_traceability.py`，抽样 + 逐跳校验，失败即红 |
| 证据 | `evkg dossier <clm_id>` 的 Markdown 输出 ×5 + `evkg audit_store` 的 `status=pass` |
| 附加 | `audit_store` 的 9 项不变量全部 0 violation |
| 负责里程碑 | M4 |
| 证据存放 | `artifacts/gates/G2/` |

### G3 · Capability Audit ★ 最关键

> 系统是否能够发现"用户说自己会，但目前证据并不足"？

这一条是产品的**立身之本**，也是最容易做假的一条 —— 所以用**对照实验**判定，而不是单点观察。

| 场景 | 输入 | 必须得到的结论 |
|---|---|---|
| **A（弱证据）** | 用户聊天说"我会 Agent Memory"，仅有论文笔记与对话，**无代码/项目/任务证据** | 理解 ≥ ⭐⭐，实践 ≤ ⭐；理由中必须显式指出"缺少实践证据" |
| **B（强证据）** | 同一用户，补充一个含 Memory 实现的 GitHub 项目 | 实践星级 **显著高于** 场景 A（≥ +2 级） |

| 项 | 内容 |
|---|---|
| 判定 | A 与 B 两次 assessment 的对照结果符合上表；A 不得给出"实践 ≥2 星" |
| 为什么要对照 | 只有 A 通过可能是"分数都低"；只有 B 通过可能是"分数都高"。**A、B 同时成立才证明系统真的在区分证据强度** |
| 证据 | 两次 `g_assessments` 记录 + 两份 dossier 对比（支持证据 / 不足 / 攻击结果）+ 输入源清单 |
| 反例 | 系统把 `confidence` 直接当星级 → 场景 A 会被误判为高实践星级 |
| 负责里程碑 | M4 |
| 证据存放 | `artifacts/gates/G3/` |

### G4 · Task Quality

> 给出的任务是否真正针对能力缺口？

| 项 | 内容 |
|---|---|
| 正向判定 | 每个 task 可反向映射到 ≥1 个 gap；task 必须含 {可交付物, 预计时长, 验收方式} |
| **反例（必须被拒）** | "去学习 Agent Evaluation" 这类**不可验收**的任务 —— 生成器必须拒绝或改造它 |
| 检查 | 对生成的 task 集合逐条跑规则校验，记录通过率 |
| 证据 | task 列表 + gap 映射表 + 反例拒绝日志 |
| 负责里程碑 | M5 |
| 证据存放 | `artifacts/gates/G4/` |

### G5 · Growth Loop

> 完成任务之后，Evidence 增加 → Capability 变化，是否能够自动发生？

| 项 | 内容 |
|---|---|
| 判定 | 端到端跑通一次：gap → 生成任务 → 提交产物 → 新证据 → 重新评估 → **≥1 个能力星级变化**，**全程无人工干预** |
| 附加 | 变化能归因到具体的新证据（哪份提交、哪条 claim 导致） |
| 证据 | 前后两份 assessment（带时间戳）+ 新 source 记录 + 归因链 |
| 反例 | 星级变化但无法说明原因；或需要人工改库才变化 |
| 负责里程碑 | M5 |
| 证据存放 | `artifacts/gates/G5/` |

### G6 · User Return Value

> 用户过几天回来之后，能不能得到"你发生了什么变化，以及接下来该做什么"？

| 项 | 内容 |
|---|---|
| 判定 | 模拟隔天返回，系统输出同时包含：① 变化摘要（对比 growth snapshot diff）② 下一步建议 ③ 引用到长期偏好 |
| 证据 | growth snapshot 前后 diff + Growth Agent 输出 + 会话截图 |
| 负责里程碑 | M6 M7 |
| 证据存放 | `artifacts/gates/G6/` |

## 4. 质量门（工程侧，与产品门并行）

| ID | 门 | 判定 | 触发时机 |
|---|---|---|---|
| QG1 | 证据不变量 | `evkg audit_store` → `status=pass`，9 项检查 0 violation | 每次评估流程后 |

| QG4 | 无密钥入库 | 仓库与账本中无明文 token/密钥；`.env` 已 gitignore；日志脱敏 | 每次提交前 |
| QG5 | 全量测试 | `uv run pytest` 全绿（含 evkg 自身的 31 项） | 里程碑收口 |

## 5. 验收记录格式（落 PROJECT_ACCEPTANCE.md）

证据索引行：

```
| EV-007 | 2026-xx-xx | 运行 tests/test_assessment_rules.py -k g3_ab | exit 0, 14 passed | commit abc1234 | G3 对照实验 A/B 均符合预期 | artifacts/gates/G3/ | 90d |
```

Gate 记录行：

```
| G3 | 2026-xx-xx | 能力审计对照实验 | Assessment 评级引擎 | 通过 | EV-007 | — |
```

**有效期**：产物类证据默认 90 天；一旦代码变更触及被验证的逻辑，证据立即失效，需重跑。
